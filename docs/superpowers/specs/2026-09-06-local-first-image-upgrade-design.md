# 纯文字空间首次本地图片同步：v2 → v3 设计补充

日期：2026-09-06

状态：用户已确认交互与升级方向；本书面补充待用户审阅。尚未实现，不是发布或验收证明。

关联设计：[引用图片同步 v3](2026-09-04-referenced-image-sync-v3-design.md)。本补充只修订该设计的空间级协议选择与首次本地图片升级路径；其余范围、权限、限额、引用语义和兼容规则继续有效。

## 1. 目标与明确选择

一个只含文字、仍使用 v2 的 Space，在 Obsidian 中首次添加受管图片引用后，应直接进入统一升级预览。用户一次确认，即授权预览所列的页面/目录变化、引用图片上传、首个 v3 Revision 发布及本地应用，不要求先去网页上传图片，也不要求先单独发布一个空的 v3 中间版本。

选择：复用现有公开 v2 固定快照读取和 v3 Push session，通过插件内显式升级协调器连接两者。服务器一次 Finalize 原子发布完整候选；成功验证后才提交本地 v3 基线。

不选择：先独立升级再 Push。该方案增加中间版本与确认步骤，并不能复用目前只接受远端图片候选的 bootstrap 入口完成纯本地图片升级。

不做：通用附件目录同步、后台无确认升级、修改 v1/v2 wire/hash、将 v2 hash 冒充 v3 hash、GET 隐式发布、删除未引用文件、按同名猜测远端附件身份、强行绕过旧服务器的图片拦截。

## 2. 已核对的现状与契约验证门

插件实现检查基点为 `6e4510e`。当前 `main.ts` 根据服务器 capabilities 选择运行时，没有完整保留 Space 的 `syncMode`；普通 `previewPushV3()` 则要求已有 v3 基线并读取 v3 head。这两点不能直接用于尚未升级的纯文字 Space。

主项目 release 工作区的公开接口实现表明：v3 create-session 将 `baseRevision` 与当前 head ID 比较；Finalize 在 Space 锁内重新读取当前候选、应用 changes、验证精确 delta，然后通过 v3 writer 发布。因此，本设计不预设必须新增服务器端点或发布新版协议包。

这是源码支持的可复用方向，不是跨协议端到端验收结果。实施第一道契约门必须证明：公开 v2 固定快照所表达的树，经过显式字段映射后，与服务器用于 v3 Finalize 的 legacy base 候选语义一致，尤其包括目录顺序、Page/Folder ID、路径、正文、时间戳与精确 delta。不得用 FakeRemote 预选成功替代该证明。

当前依赖仍为已发布 `@neomei/agentwiki-sync-protocol@0.5.1`。新增的是插件私有升级状态，不向现有 wire 加桥接字段。若契约验证发现公开数据不足，先在插件项目记录最小公开契约需求，再经主项目独立任务处理；不得复制服务器内部实现或私自放宽校验。

## 3. 服务器能力与 Space 模式分开判断

| 条件 | 路径 |
| --- | --- |
| 服务器仅支持 v1/v2 | 维持既有协商；任一端有候选本地图片即阻止同步 |
| v3 服务器，Space 为 `legacy_v2`，双方无受管图片候选 | 使用严格校验过 capabilities 的真实 v2 adapter |
| v3 服务器，Space 为 `legacy_v2`，本地有受管图片候选 | 本补充的 local-first 升级协调器 |
| Space 为 `bootstrap_required` | 既有远端候选 bootstrap 预览/确认，再固定版本 Pull 预览/确认 |
| Space 为 `native_v3` | 正常 v3 同步，即使当前附件集合为空也不降级 |

规则：

- 保留并严格解析公开 Space `syncMode`；模式、权限和 currentRevision 必须属于当前 server/Space，不能由错误文本猜测。
- 全程使用现有 Human Device Credential；只读用户可以查看允许读取的预览，但升级确认必须禁用。客户端权限提示不代替服务器在 session/Finalize 时重查权限。
- 服务器级 v3 capabilities 缓存不因某个 legacy Space 使用 v2 而改写。v2 capabilities 单独读取、校验，不将 v3 限额对象强制转换为 v2。
- 本地已提交 v3 generation 的映射不得因远端返回 legacy 模式而降级，应报告不一致；未完成升级日志优先进入恢复，不能选普通 v2 运行时绕过它。
- 401/403/409/429/5xx、网络异常、未知模式、损坏响应均不是降级信号。
- `bootstrap_required` 的状态页与策略入口必须在请求不合法的 v3 head/delta 之前进入 bootstrap 路径；只读查看不能触发发布。
- legacy 模式下解析本地 Markdown 候选用于分流，只在发现的有效引用上读取图片字节。远端固定正文若出现图片候选，与 legacy 模式不一致，则刷新模式并重新预览，不把它当作空附件树继续升级。

## 4. 读旧版本，构造新候选，不提前改基线

### 4.1 固定远端和本地输入

读取当前 v2 head 得到基线 Revision ID `R`；后续所有快照分页固定到 `R`。验证协议版本、Space、分页完整性、计数、正文 hash 和 v2 manifest hash，拒绝跨版本混页、超限或不完整快照。

已有本地映射使用其经过校验的旧基线 B、当前本地 L 与远端 R 做三方合并。首次绑定且尚无 B 时，复用既有显式初始绑定规则，展示冲突并保持已存在远端对象身份；不得按同名静默覆盖本地笔记。真正的空空间仅接受公开空 head 的严格证据（revision `0` 与零计数），不能把 404/权限失败解释成空树。

所有本地输入记录 scoped 路径与 before-state/hash/扫描代次，包含目录操作的后代闭包。映射根、身份、凭据绑定和本地最低协议要求共同绑定预览。

### 4.2 分离三类 hash 与版本身份

使用明确的本地 `LegacyUpgradeBase` 类型，保存 `sourceProtocolVersion: "2"`、`sourceRevision: R`、v2 完整性证明及校验过的树。它不是已发布的 `TreeSnapshotV3`，不得写入 current generation，也不得通过普通 v3 snapshot 读取接口对外呈现。

在独立计算步骤中，将受支持字段显式映射为 v3 计算输入：保留 Folder/Page 稳定 ID、路径、正文及协议要求的元数据；经过引用解析验证后，远端 legacy Page 的 `referencedAttachmentIds` 为空，远端附件投影为空。用公开 v3 canonical/hash 函数重新计算本地投影 hash。

三个概念必须分别命名和存储：

1. `sourceV2RevisionHash`：证明读取到的旧快照完整。
2. `projectedV3BaseHash`：本地转换计算的完整性证据，不宣称是服务器为 R 发布的 v3 hash。
3. v3 `confirmationHash`：绑定 `baseRevision: R`、capabilities 和确切 changes，遵守现有公开算法。

不能改动旧字段含义或在原 v2 JSON/hash 中塞入附件。最终服务器返回的新 Revision `R3` 及其 v3 hash 才是持久本地 v3 generation 的权威来源。

### 4.3 合并与图片计划

在内存/私有暂存中完成三方合并、初始绑定、引用解析、图片校验和全部冲突选择，生成最终候选 C。推送 changes 必须是远端 R 的转换候选到 C 的规范精确 delta，而不是 B 到 L 的差异，也不能把全部未改 Page 重写一次。

只处理 `pages/**/*.md` 引用且解析到映射根 `assets/<single-file-name>` 的 PNG/JPEG/WebP/GIF。未引用图片不读字节、不上传。新图片 ID 一旦绑定确认，不在重试中变更；已有合法身份遵守当前 active/pending/inactive 所有权规则，不以不同内容的同名文件冒领身份。

v2 读取受 v2 限额约束，v3 候选/Push 受 v3 限额约束；共有资源采用适用限制的较严者。原设计的 10 MiB/Blob、1000 张/Revision、100 MiB/次、1 MiB/chunk、最多10块、单边10000px、4000万像素及默认并发2均保留，服务端只能收紧。

若冲突选择后 C 不再包含任何受管图片，不发布一个仅为升级而存在的 v3 Revision；使升级预览失效，返回正常文字同步预览并要求重新确认。

## 5. 一次确认的精确授权范围

预览必须显示：空间将从 v2 升级为 v3、页面/目录变化、图片名称及数量、计划传输字节上界、冲突决策和本地将应用的变化。明确说明升级成功后该映射不自动降级；包含图片的版本要求支持 v3 的客户端。

按钮语义为“确认升级并同步”。不存在独立、先行的升级发布按钮。正常成功路径一次确认，不再为同一份未变候选要求第二次发布确认；这不改变原远端 bootstrap 路径的既有双阶段确认。

确认前：允许只读远端请求和 scoped 私有预览暂存；禁止创建上传会话、上传图片、发布远端 Revision、写入业务 Markdown/图片或切换本地基线。

确认后，首先持久化严格升级意图及其确认绑定，再开始可恢复传输。创建 session 和 Finalize 前均重验远端模式/head、capabilities、权限以及确认绑定的本地输入；任何影响候选或本地应用计划的变化都要求新预览和新确认，不在原确认下替换内容。

第一次升级不忽略“Push 前必须 Pull”：必须完成固定远端内容读取、校验和三方合并，只是不要求先把中间合并结果写入 Vault 或提交一个临时 v3 本地基线。

## 6. 提交顺序与恢复边界

正常顺序：只读预览 → 用户确认 → 持久升级意图 → 上传引用 Blob 与 changes → 远端原子 Finalize → 校验固定 R3 快照 → 应用同一确认的本地计划 → 提交 v3 基线/身份 → 完成。

### 6.1 远端提交

复用现有 v3 Push session/create、分块上传、batch、Finalize、session 查询和 abort。一个升级操作绑定一个幂等键及一份 confirmation，不为重试创建第二份发布。

服务器 Finalize 负责在同一事务/Space 锁下再次检查权限、R 是否仍为 head、完整 Blob、引用集合和精确 delta，原子写入首个 v3 Revision。不能发布只含 Markdown、缺失 Blob 的中间 head。

### 6.2 本地应用与激活

Finalize 后回读**返回的固定 R3**，而非此时可能已前进的 current；验证 v3 manifest、正文、附件元数据、计数与确认候选一致后，才进入本地事务。

本地只应用确认时已列出的计划，并检查 before-state。正常恢复采用既有可恢复 Vault 事务、身份文件及 generation pointer 机制；本地事务和 v3 baseline 共享可校验的事务归属。图片身份与已提交 R3 的关联不能先于完成证据生效。

如果服务器提交后用户又改动本地受影响文件，保留这些新改动，不覆盖、不重推旧候选。状态保持“远端已发布，本地待处理”；恢复可应用尚未冲突的原计划，但新的覆盖/合并决定必须重新预览确认。本地回滚只能恢复本次事务自己的未完成写入，不能回滚服务器 R3 或删除后来的文件。

### 6.3 私有升级状态

新增独立的本地 `local-image-upgrade` 状态模块，位于当前 device/Space 的 `.agentwiki` 控制域。使用新的严格 schema（首版 `schemaVersion: 1`）、现有 envelope/hash/双候选机制；未知未来版本阻止继续，不覆写为已知版。

持久信息包括操作 ID、server/Space/device 绑定、源 R/v2 hash、旧基线指针证据、转换证据 hash、v3 confirmation、候选及本地计划 hash、scoped payload 引用、关联 Push/本地事务 ID、阶段与发布结果校验证据。远端 session/result 的权威记录引用关联 Push journal，不单独复制成另一份可自行推进的发布状态。不写入凭据、Authorization、签名 URL、绝对 Vault 路径或日志中的图片原始字节。正文和 Blob 仅通过既有受控暂存保存，不嵌入日志。

升级协调器只拥有“跨协议阶段及归属”；Push journal 仍独占远端 session/receipt/result 事实，本地事务仍独占文件应用事实，不维护三份彼此独立的成功布尔值。升级意图必须先持久化，再派生具有相同操作归属的子事务；重启后严格校验关联，缺失/冲突证据停止并保留现场。

| 恢复时已证实的事实 | 行为 |
| --- | --- |
| 仅有未确认预览 | 不上传、不发布，可重新预览 |
| 已确认且传输未完成 | 仅恢复同一候选/会话；输入改变则中止旧会话并重新预览 |
| Finalize 结果不明 | 先查原 session；未知/网络失败保留 pending，不创建新发布 |
| 原 session 已发布 | 校验原 R3 并继续本地应用；不得再发布，也不得恢复普通 v2 写入 |
| 明确未发布且 abort/expired 已核实 | 原操作终结为 superseded，旧基线不切换；新操作必须重新确认 |
| 远端成功、本地应用失败或有新编辑 | 保留发布证明及本地文件，继续受保护的本地恢复/冲突处理 |
| 文件、身份及 v3 generation 已一致提交 | 标记完成，定向清理本操作暂存；下一次使用正常 v3 路径 |

取消规则沿用原设计：确认前及可取消传输阶段可取消；Finalize 发出后不能把取消显示为“未发布”，先查明结果。本地事务进入不可取消阶段后必须到达安全终态。

即使重启时当前 Space 已变为 native_v3，也必须先恢复未终结升级。当前 head 后续前进不影响恢复原固定 R3；完成后再正常 Pull 最新版本。其他设备抢先升级使 R 过期时，原确认作废并重新按公开模式路由。

## 7. 代码与仓库边界

插件新增独立的升级计算/协调模块、私有状态仓库和专用测试，避免把转换、恢复和 UI 再全部堆入 `SyncRuntime`。预期职责为：

- 空间路由：保留 `syncMode`、分别校验 v2/v3 capabilities、根据本地最低协议及未完成日志选择流程。
- 升级计划：校验固定 legacy 输入、显式转换、三方合并、输出候选及本地动作，无外部写入。
- 升级协调：一次确认后的远端/本地事务串联与恢复，不复制 Blob 传输或事务引擎。
- 升级状态：严格持久 schema、归属和清理规则。
- UI：统一预览及状态提示，复用现有冲突交互，所有确认与取消路径可实际操作。

实施计划确定最终文件名与最小公开端口调整。协议包、服务器内部代码、用户主 Vault 均不是插件直接导入或修改的对象。本补充不授权在设计步骤部署或发布任何组件。

## 8. 测试与完成门

1. 转换与计划：v2/v3 hash 明确不同且分别正确，ID/目录元数据保真；精确 delta、初始绑定、三方冲突、候选全被取消、不同 hash 不冒认身份。
2. 真实入口的受控 HTTP 测试：从插件 factory/同步中心走各 Space 模式，断言协议探测及读取次序；legacy 文字流可用、local-first 可达、bootstrap 可达、native 不降级。确认前 session/Blob/业务写入全部为零。
3. 服务器公开契约集成：固定 v2 Snapshot → 实际 v3 Push → 首个 native v3 Snapshot；验证一个操作仅新增一个 Revision，非修改 Page 保留，网页解析图片正确。契约缺口不能靠测试 fake 迁就。
4. 故障注入：意图持久化、create 响应丢失、Blob/batch、Finalize 响应丢失、固定 R3 读取、Vault 图片/正文写入、身份提交、generation 切换各边界中断并重启。包括权限撤销、capability/base 变化、双设备抢先升级及用户后续本地编辑。
5. 回归：v1/v2 原有无图路径、v3 原有图片路径、detach/re-reference、未引用图片零读取/传输，以及当前 Task19 尚未通过的独立审查项。
6. 真实桌面：从**网页端无任何图片引用**的 Space 开始，只在隔离 Vault 添加 Markdown 引用图；实际预览/确认后网页可见、离线可见、重复同步零操作。不能用先在网页引用图片转换 native v3 的 fixture 冒充本场景。
7. 真实 Android：同一最终候选执行首次本地图片升级、Vault/FileManager、窄屏确认及恢复；锁屏或桌面模拟不算验收。
8. 最终完整质量门、独立 task/fix review、whole-branch review 通过后，才沿既有 tag workflow 发布并核对资产、安装 bundle 与各渠道；本补充文档通过不代表 Task19 完成。
